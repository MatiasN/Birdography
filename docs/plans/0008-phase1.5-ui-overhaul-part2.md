## 2. Current state

- **Catalogue** (`pages/Photos.tsx`): calls `GET /photos` with no parameters, so it shows the newest 50 photos and
  nothing else. It holds the upload button (plan 0007 D8). Tiles show date, camera and "No position"; no species.
- **Upload:** one file per `POST /photos` (multipart `file`), sequential, through `fetch`, so there is no upload
  progress. Errors are collected into one `Alert`. A duplicate answers 409 with no hint of which photo it is.
- **API filters** (`PhotoFilters`): `species_id` (one), `camera` (exact), `taken_from`/`taken_to` (compared with the
  UTC `taken_at`). No "has a position" filter, no total count, no list of cameras.
- **Species:** `GET /species?q=` searches the three names, accent- and case-insensitive; `POST /species` creates;
  `PATCH /photos/{id}` with `species_ids` assigns them in order. `PhotoOut` carries only `species_ids`, so showing
  names would need one request per species. Species are **shared by all users** (no `owner_id`), and any user can
  create or trash one.
- **Dev seeder** (`backend/devtools/seed.py`): photos with GPS, dates and cameras, but no species.
- **Mockups:** `frontend/design/` shows the Part 2 Catalogue (search, *Any date*, camera, *Any position*,
  "312 photos · 58 species", "104 of 312 photos", species on the tiles) and Upload (drop zone, batch species with
  search and "Add “garç” as a new species", per-file chips, *Done* / percentage / *Waiting* / *Already in your
  catalogue*, "2 of 6 uploaded", *View in catalogue*).
- **RAW+JPEG pairs:** Phase 1 ticks "RAW+JPEG pairs uploaded as one photo", but there is no code for it: `ingest`
  stores one file per photo, and no test or plan covers pairing (plan 0002 §6 left it as a follow-up). See D12.
- Tests: 163, 100% coverage gate.

## 4. API changes

Small and backward compatible; the Map and the current client keep working.

| Change | Why |
|---|---|
| `PhotoOut.species`: `[{id, scientific_name, name_en, name_pt}]` in the photo's order, next to `species_ids` (D1) | Tiles, the detail and the upload list show names without a request per species |
| `PhotoFilters.located: bool \| None` | The *Any position* filter: with or without a position |
| `PhotoFilters.date_from`, `date_to` (dates, inclusive) over the local date of `taken_at_local` (D7) | "Photos from 14 Nov" means the day on the camera, not in UTC |
| `PhotoFilters.species_id` accepts several (`?species_id=1&species_id=4`), any of them | Searching "heron" can pick more than one species |
| `GET /photos/summary` with the same filters → `{photos, species}` (D2) | The mockup's "312 photos · 58 species" and "104 of 312" |
| `camera_make`, `camera_model` columns and filters; `GET /photos/cameras` → `[{make, model, photos}]`, the user's cameras, most used first (changed 2026-11-17: brand and model only, no filters on ISO, shutter or aperture) | The camera filter's options |
| `POST /photos` accepts an optional `species_ids` form field (D8) | Species set in the same request as the upload |
| 409 on a duplicate answers `{detail, photo_id}` (D10) | *Already in your catalogue* can link to the photo |

All of it gets pytest coverage like the existing endpoints; `alembic check` stays clean (no schema change).

## 5. Species picker and the photo detail

**`SpeciesPicker`** (ours, on shadcn `Popover` and `Input`, D6): an ARIA combobox. Typing searches
`GET /species?q=` (debounced, 200 ms); each option shows the English name, then Portuguese and Latin in muted text,
as in the mockup. Arrow keys, Enter and Escape work; picked species are chips with a remove button. When nothing
matches, the last option is **Add “…” as a new species**, which opens a small form (the scientific name and
at least one of the English and Portuguese names, required by the API too; changed 2026-11-17), the typed text
prefilled in the field it most likely belongs to) and calls
`POST /species`. A 409 (the name exists) selects the existing species instead.

**Photo detail:** a *Species* section above *Details*, as in `photo-wide.webp`: chips, *Add species* opening the
picker, removing with the chip's ×. Each change is one `PATCH /photos/{id}` with the new `species_ids`; the panel
title becomes the first species' English name (falling back to "Photo details").

## 6. Catalogue tab

- **Filter bar** as in the mockup: species search (the picker in filter mode: choosing narrows the grid, no
  "add new"), *Any date* (a popover with *From* / *To* date inputs and shortcuts: this year, last 30 days),
  camera (options from `/photos/cameras`), *Any position* (*With position* / *Without position*). An active filter
  shows its value and an × to clear it. On phones the buttons scroll sideways under the search field.
- **Filters in the URL (D4):** `?species=1,4&from=2026-01-01&to=2026-11-17&camera=Nikon%20Z%208&located=false`,
  next to `?photo=`. Back undoes a filter change, a link or reload keeps them. Changing a filter replaces the
  history entry rather than pushing one per keystroke.
- **Counts:** "312 photos · 58 species" by the heading (unfiltered), "104 of 312 photos" at the end of the bar when
  a filter is on, both from `/photos/summary`.
- **Paging (D3):** 60 photos per request (a multiple of the 2–6 columns). A sentinel after the grid loads the next
  page when it scrolls into view (`IntersectionObserver`); it is also a *Load more* button, so keyboard and
  screen-reader users reach it and jsdom tests can click it. The `?photo=` logic keeps fetching a linked photo
  that isn't loaded yet.
- **Tiles:** first species' English name (or *No species yet* in italics), "+1" for more, then date and camera, as
  in `catalogue.js`.
- **The upload button leaves.** The header gets *Upload* as a link to the Upload tab on wide screens; on phones the
  tab bar already has it.

## 7. Upload tab

As in `upload-*.webp`:

- **Choosing files:** a drop zone over the whole tab on wide screens (the dashed box highlights while dragging) with
  *Browse files*; on phones *Choose photos* opens the photo picker (`<input type="file" multiple accept=…>`;
  `capture` is left off, so the library is offered and not only the camera). The size limits from `/health` are
  shown and checked before sending, as today.
- **Queue:** every file gets a row (thumbnail made in the browser for JPEG/PNG/WebP with `createImageBitmap`, an
  icon otherwise), name, size, its species chips and a status: *Waiting*, a percentage with a bar, *Done*, or the
  error (*Already in your catalogue* with *Open*, *Too large*, *Not a photo*, network errors with *Retry*).
- **Progress (D9):** `fetch` can't report upload progress, so uploads go through `XMLHttpRequest` with
  `upload.onprogress`, in a small `uploadFile()` in `api.ts` that keeps `api()`'s 401 → login handling. **Two
  files at a time**: enough to keep the line busy with 50 MB RAW files without starving the server's ExifTool.
- **Species:** *Species for every photo in this batch* (the picker) applies to every file still waiting; each row's
  chips and *+ Species* change one photo. For a file already uploaded the change becomes a `PATCH`.
- **Leaving the tab:** the queue lives in a context above the routes, so switching to the Catalogue doesn't stop
  it, and the Upload tab's icon shows a small progress badge while files are going. Closing or reloading the
  browser tab while uploading asks for confirmation (`beforeunload`).
- **Header:** "2 of 6 uploaded" and *View in catalogue*, which opens the Catalogue with the newest first.
- Thumbnails still being made in the background are refetched once after 2 s, as the Catalogue does today.

## 11. Decisions (confirmed 2026-11-17)

All follow the recommendation. D11: no release badge for now. D12: pairing is built in this plan (step 6).

| # | Question | Recommendation |

| D2 | Counts | A `/photos/summary` endpoint. An `X-Total-Count` header on the list would give the photo count but not the species count. |

## 16. Implementation notes (step 2: API and seeder)

- **Brand and model.** There was only `camera`, built from EXIF `Make` + `Model` and often ugly ("NIKON CORPORATION
  NIKON Z 8", "SONY ILCE-7S"). Now `camera_make` is the brand as people write it, from `BRANDS` in `app/exif.py`
  (the first word of Make, or of Model when that starts with a brand: Ricoh writes Make "RICOH IMAGING" for its
  Pentax bodies). `camera_model` is the model without the brand, and `camera` is the two joined ("Nikon Z 8"). An
  unknown brand keeps Make as written. The `camera` filter is replaced by `camera_make` and `camera_model`; no
  frontend used it.
- **Migration 0013** adds both columns and fills them from the EXIF already in `photos.exif`, in plain SQL with a
  frozen copy of `BRANDS`, so `alembic upgrade --sql` still works. Photos whose tags name no camera keep their
  value. `test_migrations.py` runs the backfill over every case in `test_exif.CAMERAS` and checks it matches the
  Python. The real RAW samples now read "Nikon Z5_2" and "Sony ILCE-7S".
- **Duplicates:** the content hash is unique across all accounts (plan 0002), so a 409 can come from someone
  else's photo or one in the trash. `photo_id` is included only for the user's own, visible photo. Pointing at
  another account's photo would reveal that it exists. Left as it was, for a later decision: a photo in the trash
  still blocks uploading the same file again, and one account's upload blocks the same file for everyone else.
- **Species:** `SpeciesIn` requires a non-blank scientific name and an English or Portuguese name, trimming spaces;
  `SpeciesOut` doesn't validate, so older records without common names still load. The scientific name now
  clashes regardless of case ("ardea cinerea" finds Ardea cinerea). A clash answers 409 with `species_id` unless
  that species is in the trash; a race between the check and the insert is caught and answered the same way.
- **Seeder:** 18 birds of Portugal with their three names, about 8% of photos without species and 12% with two,
  drawn from a random stream of their own, so existing photo numbers keep their image and position. Species are
  shared, so existing ones are reused as they are and trashed ones skipped.
- **Docs:** `CONTRIBUTING.md` has a *Catalogue filters* section and the upload's `species_ids` and 409 body.
- **Tests:** 285 backend, 100% lines and branches; `alembic check` clean.

## 17. Implementation notes (step 3: species picker and photo detail)

- **`SpeciesPicker`** (`components/SpeciesPicker.tsx`): an ARIA combobox (input `role="combobox"`, options in a
  `role="listbox"` referenced through `aria-activedescendant`), its list in shadcn's `Popover` (added with
  `npx shadcn@4.23.0 add popover`, trimmed to `Popover`, `PopoverAnchor` and `PopoverContent`). It searches after a
  200 ms pause, leaves out species already chosen, and supports arrow keys, Enter and Escape. Escape closes only
  the list while it is open, so a side panel around the picker stays. With `allowCreate`, the last option opens
  the *New species* form with the typed text in its likeliest field (a binomial goes to the scientific name, text
  with Portuguese letters or a hyphen to Portuguese, anything else to English). *Add species* stays disabled until
  the scientific name and an English or Portuguese name are filled in. A 409 that names an existing species selects
  it.
- **Lint exception:** oxlint's `prefer-tag-over-role` flags `role="combobox"`, `listbox` and `option` themselves, and
  `click-events-have-key-events` flags options that are chosen from the input's keyboard handler. The native
  elements it suggests can't show three names or an *Add new* entry. `.oxlintrc.json` turns those two rules off
  for `SpeciesPicker.tsx` only, with the reason beside the override.
- **Photo detail:** a *Species* section above *Details*: each species with its other names and a remove button,
  *Add species* opening the picker (focused) with *Done* to hide it. Each change is one `PATCH`. The panel title on
  the Catalogue and the Map is the first species' name (`photoTitle`).
- **Tiles:** the first species (or *No species yet*), "+1" for more, then "date · camera", as in the mockup.
- **API client:** `Species`, `speciesName` (English, else Portuguese, else scientific), `speciesOtherNames`;
  `ApiError.body` keeps the whole error body for the 409 fields.
- **Tests:** 190, 100% everywhere, 8 runs in a row with no failures. Not yet checked in a real browser; that's the
  manual check after step 4 (§10), which should look at the popover's position inside the side panel and the
  phone sheet.

## 18. Implementation notes (steps 4 and 5: Catalogue and Upload tab, together)

Done in one go at the user's request (2026-11-17), since the upload button had to leave the Catalogue anyway.

- **Filters in the URL** (`lib/filters.ts`): `?species=1,4&from=…&to=…&make=Nikon&model=Z%208&located=false`, next
  to `?photo=`. Each change is a new history entry, so Back undoes it; the open photo stays open. Malformed values
  are ignored, and a species in a link that no longer exists is dropped from the URL (replacing the entry).
  Only the filter part of the URL drives the list, so opening a photo doesn't reload it.
- **Filter bar** (`components/FilterBar.tsx`): the species picker without *Add new*, with the chosen species as
  removable chips under the bar; *Date* (shortcuts *Last 30 days* and *This year*, or *From*/*To* and *Apply*, so
  typing a date doesn't push history entries); *Camera* from `/photos/cameras`, grouped by brand with *All Nikon*
  first; *Position*. An active filter shows its value and a separate clear button (a button can't sit inside

## 19. Implementation notes (step 6: RAW+JPEG pairs, D12)

- **API:** `POST /photos` takes the camera JPEG as an optional `companion` file. Checks, in order: the RAW's own
  (type, size, duplicate), then the companion's: the main file must be RAW (400), the companion a JPEG by content
  (415) within the non-RAW limit (413); a refusal stores nothing. The JPEG is stored as the photo's `preview`
  (its own file name kept) after `exiftool -all= -tagsfromfile @ -Orientation` drops its metadata, the same way
  embedded previews are cleaned, so a served preview carries no GPS. The thumbnail is made from it. The reply is
  `UploadOut`: `PhotoOut` plus `warning` (also `null` for plain uploads; two tests that compared an upload's JSON
  with the list's drop it).
- **Same shot?** `exif.pair_warning()`: the RAW's and the JPEG's `DateTimeOriginal` (falling back to `CreateDate`)
  must match to the second, their `SubSecTimeOriginal` when both have one, and their camera (brand and model as
  `camera()` reads them) when both have one. A mismatch, or a missing date on either side, is a **warning in the
  reply, not a refusal**, as asked: the pair is stored and the Upload tab shows the warning under *Done* ("The
  JPEG may not belong to this RAW: taken at 17:57:07, the RAW at 17:57:05"). If ExifTool fails on the companion,
  the pair is kept too, with a "couldn't confirm" warning. The CR3 sample's embedded JPEG carries no EXIF, so the
  tests pair the NEF sample with generated JPEGs whose date and model do or don't match it.
- **Upload tab:** files added together are paired by name without the extension, case-insensitively
  (`DSC_0001.NEF` + `dsc_0001.jpg`); a JPEG added later joins a RAW with its name that is still waiting. The row
  reads "DSC_0001.NEF + DSC_0001.JPG", shows both sizes and the JPEG as the preview (the browser can't show the
  RAW), and offers *Separate* while the pair waits, which makes two uploads of it. A JPEG over the limit fails the
  pair before it is sent. Files keep the order they were dropped in.
- **Bugs found on the way:** `stem()` cut the last letter off a name without a dot (`lastIndexOf` gives -1); a
  JPEG that paired with a RAW was at first also queued on its own.
- **Not done:** a lone JPEG uploaded earlier isn't recognised when its RAW arrives later (the content hash is only
  unique among originals, so the pair is simply a second photo); and pairs aren't detected across batches when the
  RAW arrives after the JPEG.
- **Tests:** backend 297 (12 new in `test_pairs.py`), frontend 228, 100% on both sides; `alembic check` clean. Not
  yet tried in a browser: the user takes the dev stack for that.

### 19.1 Changes after review (2026-11-17)

- **The same-shot check moved to the browser**, so the user sees a likely mismatch before anything is sent.
  `src/lib/exif.ts` reads the capture time, sub-second part, Make and Model from slices of the files (a few KB,
  through `Blob.slice`, never the whole RAW): JPEG, the TIFF-based RAWs (NEF, NRW, CR2, ARW, DNG, PEF, ORF, RW2),
  CR3 (CMT1/CMT2 boxes) and RAF (through its embedded JPEG). Our own ~200 lines rather than a library: installing
  one wasn't possible here, and this needs four tags. On the four real samples it reads what ExifTool reads.
- **Upload tab:** a pair shows *Checking…*, then goes if the files match. If they look like two shots it waits
  (*Waiting for you*), with a notice in its row ("…taken at 17:57:07, the RAW at 17:57:05. Upload them as one photo
  anyway, or each on its own?") offering *Upload as a pair* and *Separate*, and a line above the list counts the
  pairs waiting. Other files keep going meanwhile. When the files can't be compared (a format or a file without a
  date), a quiet note says so and the pair goes ahead. A check that finishes after the pair was separated is
  ignored.
- **Server:** `exif.pair_warning` stays and its result is only logged (`app.photos`, with the stored file name);
  `POST /photos` answers a plain `PhotoOut` again, so the `warning` field and `UploadOut` are gone.
- **nginx limit:** a pair is one request of up to 70 + 40 MB, over the old 75m `CLIENT_MAX_BODY_SIZE`. The default
  is now 115m (Dockerfile, compose, `.env.example`, CONTRIBUTING), documented as "above `MAX_RAW_UPLOAD_MB` +
  `MAX_UPLOAD_MB`". If an install's limit is still too low, nginx's own 413 (no JSON) shows as "Too large for the
  server's request limit", and *Separate* is offered on failed pairs too, so the RAW and the JPEG can go one by one.
- **Roadmap:** the cross-upload pairing left out above is now a Phase 4 item.
- **Tests:** frontend 249 (exif reader on the real samples and on built files of every format; held, kept,
  separated and proxy-refused pairs), backend 297; 100% on both.
